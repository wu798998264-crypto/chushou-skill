# LibTV 画布适配与验收

适用范围：LibTV 原生画布、素材上传、分段视频草稿与引用。平台操作仅使用官方 `libtv` CLI，不用浏览器或私有HTTP接口绕过限制。先遵守 [canvas-adapters.md](canvas-adapters.md) 的共用规则；宿主已安装 `libtv-cli` Skill 时再读其文档，但**当前 CLI 的帮助优先于旧版手册**。

## 启动与版本

1. 先找 PATH 中的 `libtv`；未找到时检查当前用户的 `~/.libtv/libtv`，Windows 为 `%USERPROFILE%\.libtv\libtv.exe`。不写死作者用户名或机器目录，也不能把不在 PATH 误报成未安装。
2. 读取 `--version`、`--help`、`node --help`、`node create --help`、`upload --help`。不同版本存在不兼容选项：官方1.2.0已移除 `--right` 系列，统一从下游执行 `node <target> --left <source>`。
3. 官方安装发现入口是 `https://api2.liblib.art/api/www/landing-activities/getById?id=240`；解析外层 `data.linkUrl` JSON 中的 `version`、`install` 和 `skill` 完整URL。需要安装或升级时按对应官方安装文档执行，不猜最新下载地址；保留既有凭据，不把登录信息放进素材包、日志或发布仓库。
4. 用 `account info` 检查当前登录及账户；需要排障且版本提供时用默认脱敏的 `status`。不要为常规适配打开 `--verbose`／`LIBTV_DEBUG`，其输出可能含请求与凭据。未登录时记录登录阻断，不将离线准备称为原生绑定成功。
5. 记录实际画布UUID，运行命令显式传 `-p <UUID>`。`project` 是画布，`workspace` 是装画布的工作区；`project list -p` 的 `-p` 是页码，不能混用。保留用户指定的账户、团队与项目，不自动切换。涉及画布时向用户提供 `https://www.liblib.tv/canvas?projectId=<UUID>`。

CLI 1.2.0及其帮助、官方同版本文档已于2026-10-25实测；这是能力快照，后续运行仍须重新读取。

## 原生草稿与生成引用

1. `model search --type video` 获取展示名，再用 `model <唯一模型名或key>` 读取完整 schema。`-s model=...` 使用搜索结果的**真实展示名**；不要把 `model` 命令外层返回的 `modelName` 当成始终可写的展示名，已观察到它返回key而 `schema.modelName` 才是展示名。模式、整数时长、比例、清晰度和参考上限都按本次 schema。
2. 将分镜预计时长按四舍五入转整数后，核验当前模式的可用时长。若计划4秒而模型最低5秒，或者计划超过该模型上限，记录冲突并调整方案；不能悄悄截断。16:9显式写入，不能依赖可能是 `adaptive` 的模型默认值。
3. 一段一个 `video` 节点；`--x`／`--y` 写在父命令 `node` 后、`create` 前。同一版本的段落同X、Y逐段递增；旧版本、任务和结果保留，新版本放右侧。
4. 本地真实文件通过 `upload` 建资源节点。记录本地SHA256、远端 `nodeKey`、上传返回的类型／尺寸／时长。相同SHA在当前画布复用同一节点，连接多张下游卡；不能只用名称判断同一资产，也不能把多个不同文件绑定到同一 `nodeKey`。
5. 将**本段实际模型参考白名单**连入生成节点，不能把溯源图的所有边复制过来。`--left` 只确保边存在，**不会替换已有入边**；更新前后都读取画布实际边与节点 `imageList`／`videoList`／`audioList`。额外入边会触发引用重算，不能靠未在提示词提及来排除。用户现有节点含意外入边时优先新建本次草稿，不清空用户连线。
6. 在文内对应位置写 `{{Node <真实nodeKey>}}`；其节点须已连到本段。唯一名称也可写 `{{Node "展示名"}}`，但跨版本和同名素材优先真实key。key是平台不透明标识，已实测UUID和 `i-...`／`a-...`／`v-...` 短key，不以展示名、类别编号或自造ID替代。
7. 用 `--prompt`／`-s` 写生成栏参数；`-u content=...` 是文本节点显示内容，不能代替视频提示词。不要另外复制完整提示词到文字卡。CLI会把写入的Node引用编译成平台媒体标记，查询时再还原为Node引用；以回读key和媒体数组为准，不自行写 `{{Image 1}}`。
8. 先保存草稿，不加 `--run`，也不执行 `group --run`、`video hd`、样片转正片等会触发真实任务的操作。视频生成按用户明确要求与提交前核对规则执行。`--run` 本身同步等待终态，不能看到taskId后再次提交。

命令骨架，参数须通过进程参数数组传递，不能把用户提示词拼成shell代码：

```text
libtv upload <资产名称> -p <UUID> -t image -f <真实路径> --x <X> --y <Y>
libtv node --x <X> --y <Y> create <段落名称> -p <UUID> -t video --left <assetKey> -s model=<真实展示名> -s modeType=<真实模式> -s duration=<整数> -s ratio=16:9 --prompt <完整提示词>
libtv node <段落key> -p <UUID>
libtv project <UUID>
```

## 来源可视化与直接媒体边的区别

原视频及原帧都可作为真实媒体上传并显示。**上传视频可以作为上游连到支持它的节点**，不是“上传素材不能连线”；问题是所需的“这张截图来自这段视频”属于分析关系，而现有CLI暴露的是受节点动作类型限制的工作流边。

两种关系必须分开：分析溯源只表示来源，不应改变生成输入；CLI的工作流入边会参与下游生成参数重算，视频、图片、音频等进入对应媒体数组，即使提示词没有提及也不能假定它们不会作为模型输入。仅把边画在左侧并不能让它变成无模型作用的说明线。

2026-10-25对官方CLI1.1.3和最新1.2.0的隔离画布实测：

- 原视频上传为 `video_resource`，帧图上传为 `image_resource`；`video_resource → image_resource` 被 `action-connections` 校验拒绝。
- 将真实帧URL放入新建image节点也不能解决：`video_resource → image_generate` 同样被拒绝。
- 图片资源 → 视频生成卡可连，真实侧面方向为上游right、下游left；引用随直接入边写入生成栏。不得将原帧直连视频卡以“画完整图”，否则原帧会成为视频生成参考。
- 官方CLI尚未发现独立的无模型作用的关系边。`action`／`generatorType` 是保留字段，不能手改或调用私有接口跳过校验。

进一步只读检查官方1.2.0程序：`validateCanvasConnect` 在提交改边前调用 `canConnectNodeData`，按本地 `action_connections_default` 动作白名单判断。`video_resource` 到 `text_generate`、`video_generate`、`video_edit`、`video_clip_resource`、`script_generate` 均为允许；到 `image_resource`、`image_generate` 为拒绝。允许的组合仍需通过当前模型的媒体类型与数量检查。故已验证的失败是**CLI适配路径的本地组合校验**，不能归因为视频格式、上传失败、账户权限或额度不足，也不能据此断言网页版所有连线工具都不支持。网页端是否另外有独立关系线尚未验收；当前Skill使用官方CLI，不能借网页私有接口绕过。

若用户明确要求原视频媒体节点直接连到原帧媒体节点，当前CLI仍记录 `direct_media_provenance_bound:false` 和具体拒绝原因，不能把未支持的直接边标为通过。但**工程思路的来源可视化**可以采用下方已验证的独立说明链；用户只要求清晰的来源关系时，不应强行把此需求解释为生成输入端口连线，也不应因为直接媒体边不可用而报告来源可视化完全无法实现。

## 已验证的来源说明链

2026-10-25隔离画布已用官方CLI保存并在独立进程回读：

```text
原视频资源 → 来源说明 → 真实帧镜像展示 → 资产来源说明 → 段落映射说明
                                          ↑
                                    已有真实资产资源
```

1. 原视频和真实帧先各上传一次，按SHA记录资源 `nodeKey`、PTS和远端URL。来源说明是独立text节点，用显示内容 `-u content=[...]` 写原片名称/key、帧资源名称/key、实际PTS；原视频用 `--left` 连入该说明，不运行模型。
2. 真实帧镜像是独立image展示节点，用官方允许的 `-u url=[<已上传帧URL>]` 显示**同一文件**，`-u showGenerator=false` 隐藏生成栏，再从来源说明连入。其名称与alt明确写“真实抽帧镜像、非AI生成”、源资源key及PTS。它不产生新图，不重新上传，不更改真实帧资源。`image_generate` 是CLI创建它的节点动作，不能将此动作误写成素材由AI生成的来源。
3. 在下游新建资产来源说明text节点，将帧镜像与对应的已有真实资产都连入该说明，内容列出真实资产名称/key和实际的制作关系。正式资产应记录原始生成提示词与来源；诊断用独立合成图片只能标为计划映射示例，不能伪称实际由该帧生成。
4. 末端是独立的段落映射text节点，连接资产说明，内容逐项标出段落名、真实生成卡nodeKey、时长、比例和实际参考白名单。多段可以在一张说明卡逐行列明，或按阅读需要每段一张，避免无谓增加辅助节点。
5. **整条说明链不接入真实视频生成卡**；最后通过映射内容指向真实卡片。实际视频卡仍只保留验收资产与本段需要的音视频输入。不能把说明text、原片、原帧或镜像加入它的输入边／`textList`／媒体数组。共享资产可同时连入资产说明和多个视频卡，无需重复上传。
6. 按左→右排列说明链，与真实生成草稿分区；每张说明标明“仅查阅”。这些辅助节点仍可能具备手动生成能力，`showGenerator=false` 不是禁止执行的安全锁。生成时仅按真实段落nodeKey白名单运行，不运行包含说明节点的 `group --run` 或把说明链当作执行计划。
7. 新进程回读，核对完整说明路径存在、镜像URL等于真实帧资源URL、名称与PTS准确、共享资产只复用不新增上传。对真实视频卡做前后比对：提示词、参考数组、入边、模式、时长、比例与位置不变，且从原片沿说明链不能到达真实视频卡。CLI可能把同一modelKey输出为展示名，只有实时schema已核实的等价key/name可规范化后比较；其他差异必须调查。

隔离验证只新增两张文字说明卡，复用了既有的来源说明和帧镜像。两张真实视频草稿仅有已验收图片／本段音频，完整参数及入边在已核实的模型显示名规范化后相同，镜像与原帧共用URL，未提交任何生成。可记录 `visual_provenance_bound:true`、`verification:cli_readback`、`direct_media_provenance_bound:false`，不要把三者混为一项“已连线”。

若纯展示载体的旧默认模型已不在当前模型表，CLI可能连修改alt也校验失败。只对本次新建的**非执行辅助节点**，读取当前模型表后用合法模型参数恢复编辑并保持媒体URL不变；这不是生成授权，不得趁机更改用户的真实生成草稿。不能盲用跨版本默认模型或宣称隐藏面板就禁用了生成。

真正需要视频参考生成时可按模型schema把原视频连到视频生成卡；这会成为模型输入，可能受参考时长和计价规则约束，只有本段确实需要且用户要求时才采用。它与“只在画布保留原片用于查阅”的需求不同，不能用它补齐分析来源线。保留同步的离线 `provenance/graph.json`，映射到真实资源、说明及段落key；若说明链也因平台能力无法完成，再列出未绑定项，不伪造完成状态。

## 保存与验收边界

每次写入后，在新的CLI进程重新读取目标节点和画布摘要，核对：

- 源媒体真实URL及文件身份；可用时经官方 `download` 下载到独立目录比较SHA256，`--watermark` 根据真实会员态，不猜值。
- 正文中的Node key、全部引用数组及order、实际入边与白名单、时长／比例／模式和段落位置。
- 同一上游资产的多卡复用、未新增重复任务、节点不含未知提交状态。

隔离诊断已验证：原视频上传与官方下载回SHA256一致；图片、4秒16k单声道音频上传；同一图片用于两张视频草稿；图片／音频混合引用、4秒16:9保存；另一CLI进程回读一致；未运行模型生成。一次音频上传曾返回 `fetch failed`，先列节点确认无残留，再重试才成功；遇写入结果未知时同样先查，不能盲目重复上传。

这些检查证明服务端草稿持久化，**不等于浏览器刷新、视频播放和操作栏折叠行为已实测**。官方1.2.0帮助及文档未发现画布截图／画布图像导出命令，`download`只下载节点媒体，不能当作画布截图。仅用CLI时如实记录UI视觉验收尚未执行；不能把神思“收起操作栏”的实现字段套用到LibTV。
